# Database Design

## Core relations

- `users` owns authentication/profile data. Wallet addresses are unique case-insensitively.
- `projects` belongs to one client and can be assigned to one freelancer.
- `milestones` belongs to one project and is ordered by `sequence_no`.
- `submissions` belongs to one milestone and stores the proof hash plus review state.
- `payments` belongs to a project and usually one milestone/submission.
- `nft_certificates` belongs to the accepted submission and freelancer.
- `transactions` stores blockchain/relayer activity for payments and certificates.
- `notifications` stores per-user feed items and unread state.
- `chats` is one-to-one with a project; messages are stored in `chat_messages`.
- `disputes` can attach to a project, milestone, submission, or payment.

## Integrity choices

- UUID primary keys are generated by PostgreSQL with `pgcrypto`.
- Foreign keys keep project, milestone, submission, payment, certificate, transaction, chat, and dispute records connected.
- Composite foreign key `(milestone_id, project_id)` on `submissions` prevents submitting to a milestone from another project.
- Unique constraints prevent duplicate milestone order, duplicate certificate per submission, duplicate proof hash, and duplicate chain transaction hash.
- Check constraints validate wallet/contract/transaction hash formats and positive money amounts.
- `ON DELETE` behavior is conservative:
  - User deletion is restricted for money/work records.
  - Project deletion cascades to milestones, submissions, and chat only where the child data cannot stand alone.
  - Payment, certificate, transaction, and dispute records are preserved for audit history.

## Indexing strategy

- Composite indexes match dashboard filters: `(client_id, status, updated_at)`, `(freelancer_id, status, updated_at)`, `(project_id, status, due_at)`.
- Partial indexes keep queues fast: pending submissions, open milestones, release queue payments, mint queue certificates, unread notifications, active disputes.
- Unique lower-case indexes handle wallet and transaction hash lookups safely.
- GIN full-text indexes support project and chat search.

## API query tips

- Always paginate list endpoints with `LIMIT` and either `OFFSET` or keyset pagination.
- For infinite scroll, prefer keyset pagination using `created_at` plus `id` once data grows.
- Use `SELECT` column lists instead of `SELECT *` for dashboard endpoints.
- For project details, aggregate milestones and latest submissions in one query to avoid N+1 calls.
- Run `EXPLAIN ANALYZE` on slow queries and compare them with `db/queries.sql`.
